摄像头循迹的第一步是二值化，而二值化的核心参数是分割阈值。固定阈值在光照条件改变时会失效：同一块赛道地面在日光灯与阴天下的灰度可相差数十个灰度级，自动曝光调整后差异更明显。因此阈值需要逐帧依据当前图像重新估计。

Otsu 法（大津法）是这类自适应估计中最常用的方法之一。本文给出完整推导、判据性质的证明、在 TC264 上的整数实现要点，以及本工程中的接口、参数配置与显示侧的方向约束。

## 一、固定阈值的失效条件

设赛道由浅色地面与深色引导线构成，某行像素灰度分布如下：

```text
地面  185 190 188 192 186 ...
引导线  35  40  38  36  42 ...
```

取两者之间的任意值（如 120）均可完成分割。但该中间值并非恒定：

- 环境照度变化导致整体灰度平移；
- 摄像头自动曝光与自动增益调整改变成像映射；
- 镜头污染、反光、阴影造成空间不均匀偏移。

上述因素使固定阈值缺乏泛化性，故需由图像自身统计特性导出阈值。

## 二、灰度直方图与概率分布

设图像宽 $W$、高 $H$，像素总数为

$$
N = W \times H
$$

统计各灰度级的出现次数 $n_i$（$i = 0,1,\dots,255$），归一化后得到灰度概率分布

$$
p(i) = \frac{n_i}{N}, \qquad \sum_{i=0}^{255} p(i) = 1
$$

该表示丢弃了全部空间信息，仅保留灰度的一阶统计特性。这一简化是 Otsu 法计算量低、对孤立噪声不敏感的原因，同时也是其无法处理空间结构相关干扰的原因。

## 三、类间方差的定义与化简

取阈值 $t$，将像素划分为两类：

$$
C_0 = \{i \mid 0 \le i \le t\}, \qquad C_1 = \{i \mid t < i \le 255\}
$$

两类的概率质量与灰度均值分别为

$$
w_0(t) = \sum_{i=0}^{t} p(i), \qquad w_1(t) = 1 - w_0(t)
$$

$$
m_0(t) = \frac{1}{w_0(t)}\sum_{i=0}^{t} i\,p(i),
\qquad
m_1(t) = \frac{1}{w_1(t)}\sum_{i=t+1}^{255} i\,p(i)
$$

全图均值为

$$
m = \sum_{i=0}^{255} i\,p(i) = w_0 m_0 + w_1 m_1
$$

后一等式由 $w_0 + w_1 = 1$ 直接得到，是后续化简的依据。

定义类间方差为两类均值对全图均值的加权平方偏差：

$$
\sigma_b^2(t) = w_0 (m_0 - m)^2 + w_1 (m_1 - m)^2
$$

由 $m = w_0 m_0 + w_1 m_1$ 可得

$$
m_0 - m = w_1 (m_0 - m_1), \qquad m_1 - m = -w_0 (m_0 - m_1)
$$

记 $d = m_0 - m_1$，代入上式：

$$
\sigma_b^2 = w_0 w_1^2 d^2 + w_1 w_0^2 d^2 = w_0 w_1 d^2 (w_0 + w_1)
$$

又因 $w_0 + w_1 = 1$，故

$$
\sigma_b^2(t) = w_0(t)\, w_1(t)\, \bigl(m_0(t) - m_1(t)\bigr)^2
$$

Otsu 阈值定义为使该式取最大值的 $t$：

$$
t^{*} = \arg\max_{0 \le t \le 255} \; w_0(t)\, w_1(t)\, \bigl(m_0(t) - m_1(t)\bigr)^2
$$

## 四、判据的两项含义

$$
\sigma_b^2 = \underbrace{w_0 w_1}_{\text{类间均衡度}} \cdot \underbrace{(m_0 - m_1)^2}_{\text{类间分离度}}
$$

分离度项在阈值位于两类之间时取较大值。均衡度项 $w_0 w_1$ 在两类各占一半时达到最大 $1/4$，当两类样本数严重失衡时迅速衰减。

两项相乘使退化解自动被排除：当 $t = 0$ 或 $t = 255$ 时必有一类为空集，此时 $w_0 w_1 = 0$，评分为零。因此无需额外增加边界判断，该性质由判据本身给出。

## 五、与类内方差最小化的等价性

图像总方差可分解为类内方差与类间方差之和：

$$
\sigma_T^2 = \sigma_w^2 + \sigma_b^2, \qquad \sigma_w^2 = w_0 \sigma_0^2 + w_1 \sigma_1^2
$$

其中 $\sigma_0^2$ 与 $\sigma_1^2$ 分别为两类的类内方差。$\sigma_T^2$ 只与图像本身有关，与 $t$ 的取值无关，为一常数。因此

$$
\max_t \sigma_b^2(t)
\iff \min_t \sigma_w^2(t)
\iff \max_t \frac{\sigma_b^2(t)}{\sigma_T^2}
$$

三个优化目标等价。该等价性是 Otsu 判据具有"最优"含义的依据：最大化类间方差等价于最小化类内方差，即两类各自的灰度分布尽可能集中。

## 六、数值验证

以第一节所示的两类各 5 个像素为例。取 $t = 120$ 时，两类完全分离：

$$
w_0 = w_1 = 0.5, \qquad m_0 = 38.2, \qquad m_1 = 188.2
$$

$$
\sigma_b^2 = 0.5 \times 0.5 \times (38.2 - 188.2)^2 = 5625
$$

取 $t = 200$ 时，$w_1 = 0$，评分为 0，被排除。取 $t = 60$ 时两类仍各自纯净，评分同为 5625，表明类内方差为零时任何介于两类之间的阈值均等价。实际图像中两类灰度存在交叠，评分曲线呈单峰，最大值位置即为分割阈值。

## 七、对光照变化的适应性

判据仅依赖直方图的相对形状，不依赖灰度绝对值。当整体照度提高时，直方图的各峰向高灰度方向平移，最优阈值随之平移，因此阈值可自动跟随光照变化。

需要区分的是：阈值并非某一类别的代表灰度，而是两类分布之间的分界点，通常介于深色引导线与浅色地面之间。

## 八、直接实现的两个缺陷

按定义直接实现时，对每个候选 $t$ 重新累加两段直方图：

```c
for (int i = 0; i < 256; i++) {
    for (int j = 0; j <= i; j++)      { /* 累加前景 */ }
    for (int j = i + 1; j < 256; j++) { /* 累加背景 */ }
}
```

其一，计算冗余。每个 $t$ 的内层循环合计固定执行 256 次，总计约 $256 \times 256 = 6.6\times10^4$ 次累加。而相邻两个 $t$ 之间仅相差一个灰度级，可递推得到。

其二，除零风险。当 $t$ 较小时前景像素数为零，`foreground_gray_sum / foreground_pixel_count` 计算为 $0.0/0.0$，结果为 NaN。NaN 参与 `>` 比较恒为假，最大值可能始终未被更新，函数返回初值 0，表现为算法异常而非编译或运行报错。

此外，256 次浮点除法在 50 fps 帧率下虽可运行，但无必要。

## 九、工程实现

代码位于 `code/otsu.c`，对外接口为

```c
uint8 otsu_calculate_threshold(const uint8 *image, uint16 width, uint16 height);
```

### 9.1 递推累加

$w_0$ 与灰度累加和 $S_0(t) = \sum_{i \le t} i\, n_i$ 均满足

$$
w_0(t) = w_0(t-1) + n_t, \qquad S_0(t) = S_0(t-1) + t\, n_t
$$

故遍历 256 个候选阈值时无需重复求和。整体复杂度由 $O(N + 256^2)$ 降为

$$
O(N + 256)
$$

本工程 $N = 188 \times 120 = 22560$，递推部分仅约 $3 \times 256$ 次运算，相对直方图统计可忽略。

### 9.2 去除归一化

直接使用计数而非概率：

$$
w_0 = \sum_{i=0}^{t} n_i, \quad
w_1 = N - w_0, \quad
m_0 = \frac{S_0}{w_0}, \quad
m_1 = \frac{S - S_0}{w_1}
$$

评分与原始定义仅相差常数因子 $1/N^2$，不影响 $\arg\max$，故结论一致。该处理避免了归一化引入的浮点运算。

### 9.3 评分的数据宽度

$$
w_0 w_1 \le \left(\frac{N}{2}\right)^2 = 1.27\times10^{8},
\qquad
(m_0 - m_1)^2 \le 255^2 = 65025
$$

二者乘积上限约 $8.3\times10^{12}$，超出 `uint32` 的 $4.29\times10^{9}$。因此评分使用 `uint64`：

```c
score = (uint64)foreground_pixels * (uint64)background_pixels
      * (uint64)(mean_diff * mean_diff);
```

该路径仅含乘法，无除法，256 次循环的开销可忽略。

### 9.4 空类处理

```c
if((foreground_pixels == 0U) || (background_pixels == 0U))
{
    continue;
}
```

空类的评分为零，跳过该候选与赋予零分等价，但可避免除零产生 NaN。

### 9.5 直方图存储位置

```c
static uint32 otsu_histogram[256];
```

若定义为函数局部数组，将占用 1 KB 栈空间。改为静态存储并置于

```c
#pragma section all "cpu0_dsram"
```

所在的 CPU0 DSRAM 段，可减少栈压力并改善访问效率。

## 十、摄像头接口

Otsu 算法只依赖一块连续的内存缓冲区，与硬件无关。图像采集由逐飞 MT9V03X 驱动完成，主要参数定义于 `zf_device_mt9v03x.h`：

| 项目 | 取值 |
|---|---|
| 分辨率 | 188 × 120 灰度 |
| 图像缓冲区 | `mt9v03x_image[120][188]` |
| 采集完成标志 | `mt9v03x_finish_flag` |
| VSYNC | P02.0（ERU_CH3_REQ6） |
| PCLK | P02.1（ERU_CH2_REQ14） |
| 数据总线 | P00.0 ~ P00.7 |
| 配置总线 | P02.3 / P02.2 |
| DMA 通道 | IfxDma_ChannelId_5 |
| 默认帧率 | 50 fps |
| 默认曝光时间 | 512 |
| 默认增益 | 32 |

上述引脚与电机（P02.4~P02.7）、编码器（P10.x、P20.x）、按键（P20.6、P20.7、P11.2、P11.3）及舵机（P33.9）均无复用冲突。

采集相关中断已在 `user/isr.c` 中转发至驱动回调，应用层无需直接处理：

```text
EXTI CH3 (P02.0)  -> camera_vsync_handler()   帧同步
DMA  CH5          -> camera_dma_handler()     行数据搬运
UART1             -> camera_uart_handler()    配置通信
```

### 10.1 模块封装

`code/camera.c` 提供以下接口：

```c
uint8  camera_otsu_init(void);          /* 成功返回 0 */
void   camera_otsu_task(void);          /* 主循环调用 */
uint8  camera_otsu_get_threshold(void);
uint32 camera_otsu_get_frame_count(void);
```

任务函数的处理逻辑为：

```c
if((camera_ready == 0U) || (mt9v03x_finish_flag == 0U)) return;

camera_threshold = otsu_calculate_threshold(&mt9v03x_image[0][0],
                                            MT9V03X_W, MT9V03X_H);
camera_frame_count++;
mt9v03x_finish_flag = 0U;
```

### 10.2 命名冲突

初始版本的初始化函数命名为 `camera_init()`，编译报错：

```text
E288: "camera_init" redeclared with a different prototype
  previous declaration of "camera_init" (zf_device_camera.h:55)
```

原因是 `zf_device_camera.h` 已声明

```c
uint8 camera_init(uint8 *source_addr, uint8 *destination_addr, uint32 image_size);
```

该函数用于串口图传的解压初始化，与本模块同名但参数不同。因此引用第三方库时，自定义模块的公开函数不宜采用 `xxx_init` 这类通用命名。改名为 `camera_otsu_init()` 后冲突消除，语义也更明确。

### 10.3 图像数据的访问封装

应用层不应直接引用驱动导出的全局数组 `mt9v03x_image[H][W]`。摄像头模块另外导出三个访问函数：

```c
const uint8 *camera_otsu_get_image(void);   /* 最新一帧灰度缓冲区，行优先 */
uint16       camera_otsu_get_width(void);
uint16       camera_otsu_get_height(void);
```

显示与后续的边线提取都只依赖这三个接口，而不依赖具体驱动的符号名。更换摄像头型号、引入 ROI 裁剪或增加双缓冲时，只需修改 `camera.c` 一处。对单一实现而言，这是一层看似多余的间接，但在需要临时替换驱动做对比实验时，可以省掉分散在各处的引用修改。

## 十一、图像预览与方向约束

调试阶段把图像直接绘制到 TFT，比只看一个阈值数字更容易判断问题出在曝光、接线还是阈值本身。库函数 `tft180_show_gray_image()` 同时支持两种输出：

```c
void tft180_show_gray_image(uint16 x, uint16 y, const uint8 *image,
                            uint16 width, uint16 height,
                            uint16 dis_width, uint16 dis_height,
                            uint8 threshold);
```

`threshold` 传 0 时按原始灰度显示，传非零值时按该阈值二值化。因此二值预览不需要额外的二值缓冲区，直接复用 Otsu 的结果作为最后一个参数即可。

### 11.1 方向设置必须早于初始化

`tft180_init()` 内部依次执行两步与方向相关的操作：

```c
tft180_set_dir(tft180_display_dir);         /* 依据方向刷新 width/height 上限 */

tft180_write_index(0x36);                   /* MADCTL，写入扫描方向 */
switch(tft180_display_dir)
{
    case TFT180_PORTAIT:        tft180_write_8bit_data(1<<7 | 1<<6 | 0<<5);  break;
    case TFT180_CROSSWISE:      tft180_write_8bit_data(1<<7 | 0<<6 | 1<<5);  break;
    /* ... */
}
```

即 0x36 寄存器（MADCTL）的取值是在初始化过程中、按当时的方向变量写入的。若先 `tft180_init()` 再 `tft180_set_dir(TFT180_CROSSWISE)`，全局的 `tft180_width_max` / `tft180_height_max` 会变为 160 / 128，但硬件扫描方向仍停留在初始化时的取值，坐标范围与实际显示不再对应。

正确的调用顺序：

```c
tft180_set_dir(TFT180_CROSSWISE);
tft180_init();
```

默认方向为 `TFT180_PORTAIT`，可用区域 128 × 160；改为 `TFT180_CROSSWISE` 后为 160 × 128。缩放后的显示尺寸必须按调整后的上限计算，否则 `tft180_set_region()` 的坐标断言会失败。188 × 120 的原始帧在两个方向下分别可缩放到 128 × 80 与 160 × 102。

## 十二、执行位置的选择

```c
void app_task(void)
{
    ...
    camera_otsu_task();
    app_update_camera_display();
    ...
}
```

Otsu 计算需遍历 22560 个像素。若置于 VSYNC 中断中执行，将显著延长关中断时间，可能影响 1 ms 定时器内的电机斜坡更新与编码器采样。置于主循环则仅降低处理帧率，不改变控制环的时序特性。

调试阶段的显示策略见第十一节：整屏绘制灰度或二值图像，阈值本身不再单独显示文字。

## 十三、验证方法

烧录后首先确认串口输出 `CAM OK`（失败为 `CAM ERR`）。随后按以下条件检查阈值响应：

| 操作 | 预期现象 |
|---|---|
| 遮挡镜头 | 阈值明显下降（直方图整体左移） |
| 对准白墙 | 阈值上升 |
| 对准赛道 | 阈值稳定于某一区间，抖动超过十余个灰度级说明曝光不稳定 |
| 快速改变照度 | 阈值在一至两帧内跟随更新 |

阈值长期停留在 0，通常对应三种成因：图像接近全黑（曝光、增益或接线异常）；画面完全均匀，此时任何候选阈值都会使其中一类为空，按第 9.4 节的跳过逻辑函数返回初值 0；评分使用 32 位整数导致溢出，或除零未处理使最大值始终未被更新。在本实现下 255 不可达，因为 $t = 255$ 时背景类必然为空。

## 十四、适用条件与局限

Otsu 法包含两个隐含假设。

其一，直方图近似双峰分布。当画面存在第三种主导亮度时（大面积反光、阴影、彩色干扰物），直方图呈三峰，方法会将其中两类合并，导致阈值偏移。

其二，全局光照均匀。方法为整幅图像计算单一阈值。车载摄像头斜向下安装时，近端与远端成像亮度存在系统性差异，同一地面在不同图像行的灰度不同，行位置越高偏差越大。

常见改进均不改变 Otsu 判据本身，而是在其外围增加约束：

- **分区阈值**：将图像按行划分为若干区域分别计算，得到随行变化的阈值；
- **限定 ROI**：仅在赛道可能出现区域内统计，排除天空与远端干扰；
- **限定搜索范围**：在上一帧阈值附近（如 $\pm 40$）搜索，兼顾稳定性与计算量；
- **双峰性检验**：当 $\sigma_b^2$ 低于阈值时沿用上一帧结果，避免在无区分度的画面上产生跳变。

在实际车辆上，单一全局阈值通常不足以覆盖全部工况，需与前几行单独处理或分区策略配合使用。该部分尚未实现，完成后另行记录。

## 十五、结论

Otsu 阈值的完整表述为

$$
t^{*} = \arg\max_{0 \le t \le 255} \; w_0(t)\, w_1(t)\, \bigl(m_0(t) - m_1(t)\bigr)^2
$$

该判据成立的原因是图像总方差为常数，最大化类间方差与最小化类内方差等价。其对光照变化的适应性来源于仅依赖直方图的相对形状，而不依赖灰度绝对值。

工程实现中有三点需要注意：

1. 使用递推累加，避免对每个候选阈值重复遍历直方图；
2. 使用整数运算与 `uint64` 评分，同时规避溢出与除零；
3. 计算放在主循环，避免延长控制中断的执行时间。

阈值本身只是中间结果，后续仍需完成二值化、边线扫描、中线拟合与偏差计算。Otsu 法的作用是使该链路在光照条件变化下保持可用。
