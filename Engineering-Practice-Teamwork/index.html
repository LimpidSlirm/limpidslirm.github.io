从能写代码到能做项目：小车团队协作入门

我有的时候在想一件事，到底该如何从零开始学习怎么做一个项目。

很多同学第一次参加项目时，最先想到的是“我负责写哪一段代码”。但一个能稳定运行的小车，通常不是某个人写出一段很长的程序，而是团队把需求、接口、测试和交付组织起来的结果。

这篇文章面向会基础 C、但缺少完整单片机项目经验的同学，以课程小车为例介绍如何协作完成一个嵌入式项目。

2. 按可独立测试的模块分工

小车项目不应该简单地按“底层、控制、应用”把工作拆给不同的人。更适合初学者团队的分工方式是：每个人负责一个能够单独运行、单独测试、单独验收的模块。

以 TC264 小车的视觉部分为例，视觉模块不只是“调用摄像头”，还可能包括边线识别、路线判断等功能。摄像头模块负责初始化硬件，并通过已有接口读取图像数据；边线识别模块则调用摄像头模块提供的接口，对图像进行处理并输出边线位置或车辆偏差。

因此，摄像头和边线识别可以分给两个人：

摄像头模块比较容易独立测试，例如检查初始化是否成功、能否持续读取数据以及数据格式是否正确。边线识别模块则相对难以完全独立测试，因为它需要具体的图像数据作为输入。实际工程中，可以使用保存的图像、模拟数组或固定测试数据进行初步验证；如果没有这些数据，就很难只靠模块本身判断识别结果是否正确。

所以，“模块可以分工”和“模块可以完全独立完成”不是一回事。接口清晰可以让两个人并行写代码，但在 TC264 小车这样的实际项目中，大家仍然需要共同准备测试数据、一起上车观察现象，并协作解决摄像头、边线识别和车辆运动之间的联动问题。越接近整车功能，越不能把问题简单归给某一个模块。

一个合格的独立模块应当具备：

  1. 明确的初始化函数；
  2. 明确的输入和输出接口；
  3. 不依赖其他成员的内部变量；
  4. 可以通过单独程序、测试桩或硬件现象验证；
  5. 有自己的验收标准和问题记录。

3. 代码组织和接口规则

团队开始写代码前，应先约定目录、接口和调用层级，而不是让每个人按照自己的习惯组织代码。以 TC264 小车为例，可以采用下面的规则：

所有成员编写的功能模块都放在 code/ 中。每个模块至少要有一个头文件和一个源文件：头文件只公开其他模块必须使用的类型、初始化函数和业务接口，具体实现、临时变量和算法细节放在源文件中。其他成员不能直接访问模块内部变量，也不能绕过接口修改底层硬件状态。

app.c 可以根据项目需要实现状态机，例如待机、手动控制、循迹、避障和故障停止等状态。状态机只负责决定当前模式和模块之间的数据流，不应该重新实现电机驱动、摄像头初始化或 PID 算法。

这种分层方式还有利于代码复用。例如，电机模块只提供“设置左右轮目标”和“停止”等通用接口，手动驾驶、循迹和避障状态都可以调用它；边线识别模块只输出偏差值，后续更换控制算法时不需要修改摄像头驱动。可复用的模块应尽量不依赖具体比赛场景、按键编号或某一个状态机，这样才能在其他小车项目中继续使用。

4. Git 协作的基本规则

4.1 先理解 Git 的基本原理

Git 不只是一个“上传代码”的工具。它会在本地保存项目的版本历史，并通过提交记录保存每次修改的快照。一次常见的修改会经过以下几个区域：

工作区是当前正在编辑的文件，暂存区用于选择本次要提交的修改，本地仓库保存已经提交的版本，远程仓库则用于团队共享。git pull 通常可以理解为先获取远程更新，再把更新合并到当前分支；如果双方修改了同一部分代码，就可能产生冲突，需要人工判断并测试。

理解这些原理很重要。例如，修改文件后没有执行 git add，提交时就可能没有包含该文件；只执行了 git commit 而没有 git push，队友也无法看到本地提交；直接 git pull 后出现冲突时，也不能简单地认为是 Git 出错。

虽然 Git 可以通过 VS Code 的图形界面操作，也可以让 AI 直接执行 commit、push 和 pull，但团队成员仍然要知道这些操作背后的原理。只有理解工作区、暂存区、提交、本地分支和远程分支之间的关系，才能判断 AI 或图形界面执行的结果是否正确，也才能在冲突、误提交或版本回退时独立处理问题。

4.5 不要把生成物当源码提交

根据工程规则，源码和用户代码应放在约定目录，第三方库保持不变。构建生成的中间文件、临时日志和本地配置应由 .gitignore 管理，避免把个人环境带入团队主分支。
