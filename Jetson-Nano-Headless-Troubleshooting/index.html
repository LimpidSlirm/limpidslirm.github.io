Jetson Nano 无外设启动排障记录

这台 Jetson Nano 的载板上 4 个 USB 3.0 Type-A 口全都不工作，键盘鼠标插上去没有任何反应，显示器也接不了，整台机器只能靠 SSH 操作。麻烦的地方在于系统里还没有可登录的账户，等于连 SSH 都进不去。

下面按实际处理顺序记录，并在每一步补上对应的原理，说明结论是怎么来的、以及能推到哪一步为止。

一、故障链

  1. 没有可用的本地输入输出，也没有可登录账户，进不了系统；
  2. 有线和无线的地址落在同一网段，无线连不上；
  3. 载板上的 USB Hub 不枚举，4 个口等于不存在；
  4. 拔掉 DC 适配器整机断电，电池这一路没顶上。

二、进不去系统：登录时到底在比对什么

新烧的镜像第一次上电会进 oem-config，要求用键盘鼠标和显示器建用户、设密码。USB 口坏了，这一步就卡死。

没有用户就没有密码，sshd 也不允许空密码或未设置密码的账户登录。本地通道和远程通道同时断掉。

2.1 原理：/etc/shadow 与 crypt(3)

/etc/passwd 里密码字段只是一个占位的 x，真正的哈希存在 /etc/shadow。该文件权限是 0640、属组为 shadow，普通用户读不到，目的是不让拿到口令文件的人离线爆破。

登录时，无论走 login 还是 sshd，实际都由 PAM 栈处理，最终落到 pam_unix：

  1. 从 /etc/shadow 取出该用户的密码字段；
  2. 字段格式是 $id$salt$hash，id 指明算法（6 表示 SHA-512），salt 是随机盐；
  3. 用存下来的盐，对刚输入的密码做同样的 crypt(3) 运算；
  4. 运算结果与存储的 hash 比较，相等才放行。

盐的作用是让相同密码得到不同哈希，使预计算表失效；哈希本身单向，只能正向计算，不能反推明文。

如果把这个字段直接写成明文，pam_unix 拿到的不是合法的 crypt(3) 串，第 2 步就解析失败，认证会被拒绝。所以挂载后改文件必须写哈希，写密码本身是没用的。

2.2 操作

Windows 读不了这个分区：内核没有 ext4 驱动，也不做日志回放，所以只能挂到 Linux 下操作。

-6 指定 SHA-512。同样密码每次输出不同，是因为盐随机，属正常现象。

插回卡、上电、网线直连，SSH 可以登入了。

这个办法等于绕过本地认证，前提是设备在自己手上且能物理接触存储卡。持有这张卡的人同样可以做这件事，所以进去之后要立刻改掉密码。

三、无线连不上：同一子网上的两条直连路由

拿到 shell 后想摆脱网线，让 Nano 连电脑开的热点。降到 2.4 GHz 也连不上，或者反复超时。

3.1 原理：地址、直连路由与源地址选择

网卡从 DHCP 拿到地址后，内核会为它所在的子网装一条 scope link 的直连路由：

这条路由的含义是：目标在这个 /24 里，就直接从 eth0 发 ARP 找对方，不需要经过网关。

Windows 移动热点和网络共享（ICS）默认使用 192.168.137.0/24。网线插着时 eth0 已经占了这个网段；此时 wlan0 再去连同一个 192.168.137.0/24 的热点，内核里就会出现两条前缀长度相同的路由。

选路规则是最长前缀匹配优先，前缀长度相同时比 metric，metric 也相同时按接口顺序决定。两条 /24 完全等价，出口就变得不确定。加上源地址是跟随出口接口选的（从哪个口发就带哪个口的 IP），去程和回程可能落在不同接口上，对端看到的源地址不对，SYN-ACK 回不来。

这里有个容易混淆的点：802.11 关联和 WPA 四次握手属于二层行为，不依赖 IP 路由，本身不受影响。真正出问题的是关联之后的 DHCP 获取和 IP 层通信，表现出来的现象就是“连上了但没网”，或者反复超时重连。

如果 ip route get 显示报文从 eth0 出去，而目标其实在热点那一侧，问题就定位了。

3.2 处理

让无线走一个和 eth0 不重叠的子网。

wlan0 连上手机热点、拿到不属于 192.168.137.0/24 的地址后，两条路由不再冲突，再拔掉网线，链路稳定。

顺带记一笔：切换网卡的过程中 OLED（挂在 I2C-1，地址 0x3c）熄灭过一次，systemctl restart jetbot_stats 之后恢复。这是显示守护进程的问题，和网络无关。

四、USB Hub 不枚举

4.1 原理：一次枚举做了什么

USB 是主机主导的总线，设备不会自己“出现”，必须由主机完成枚举：

  1. 主机给端口上电（VBUS 5 V），设备把 D+（全速/高速）或 D-（低速）上拉，主机检测到电平变化，判定有设备接入；
  2. 主机复位端口，设备在默认地址 0 上响应；
  3. 主机通过默认控制端点读 8 字节设备描述符，取得端点 0 的最大包长；
  4. 主机分配唯一地址（SET_ADDRESS），此后设备只响应该地址；
  5. 读完整设备描述符和配置描述符，下发 SET_CONFIGURATION，设备进入可用状态。

Hub 本身也是 USB 设备。它必须先自己枚举成功，主机才会通过它去枚举下游端口。所以 Hub 不在拓扑里，下面 4 个口对系统来说就不存在，无论接什么设备都不会有反应。

4.2 判读

lsusb -t 读的是内核在 /sys/bus/usb/devices 下维护的设备树。这里能看到 tegra-xusb 根集线器和 M.2 上的 btusb 蓝牙模块，但载板上扩展 4 个 Type-A 口的那个 Hub 没有出现。

由此只能确认这个 Hub 没有枚举成功。可能的原因有三类：

  • Hub 的供电缺失（VBUS 没到，或板上稳压没输出）；
  • 上行链路有问题（D+/D- 断线、阻抗异常、连接器虚焊）；
  • Hub 芯片本身损坏。

仅凭 lsusb -t 分不出是哪一类。要区分，要么量 Hub 的 VBUS 和上游差分对，要么看 dmesg 里的枚举错误码（设备描述符读取失败通常指向链路或供电，完全没有出现连接事件则更可能是供电缺失），最省事的办法是换一块载板交叉验证。实际处理是换载板。

五、拔掉适配器就断电

移动测试时发现，只要拔掉 DC 适配器，整机立刻断电，风扇也停。

5.1 原理：降压级怎么工作

电池包输出 12 V，板上的电池扩展板要把它变成 5 V。这类电路通常是同步 Buck：上下两个开关管按占空比 D 斩波，经电感和电容滤波后得到输出。理想情况下

实际还要减去导通损耗和开关损耗。输出电压通过反馈网络回到控制器，控制器据此调整 D 来稳压。

所以 5 V 输出为 0 V，机理不止一种：

  • 输入没有真正到达功率级：接插件接触不良、保险丝、防反接 MOSFET 开路；
  • 使能条件不满足：EN 引脚电平不对，或欠压锁定（UVLO）判定输入不合格；
  • 控制器或功率管损坏，根本没有开关动作；
  • 保护电路动作（过流、过温）后关断输出。

单点测输出只能确定这一级没工作，区分不了上面四条。

另外，插着适配器时 5 V 正常，说明适配器那条路是通的。两条输入并联在同一 5 V 母线上，靠 OR-ing 电路（二极管或理想二极管）决定由谁来供。“插着正常、拔了就断”意味着电池这一路没能接管，问题被限制在电池输入到 5 V 母线之间。

5.2 测量

先排除测量工具本身：确认万用表电池正常、量程和档位正确，然后分级量电压。

测量点 插适配器 拔适配器
电池包输出 — 12.0 V
电池扩展板 5 V 输出 5.0 V（旁路直通） 0 V

需要说明的是，这里是空载测量。空载时若有分压支路或漏电流，读数可能偏高，结论要以带载复测为准；不过 0 V 这种结果不存在虚高的可能，判断方向是可靠的。

5.3 结论

实测把范围压到了扩展板：12 V 输入有，5 V 输出没有，说明这块板的 12 V→5 V 变换级在电池供电时不工作。

至于失效的是 Buck 主控、前级防反接 MOSFET，还是使能或保护逻辑，单看输出电压判断不出来，需要继续测功率级输入、EN 引脚电平和开关波形。

换了一块同型号扩展板后，脱线状态下 5 V 输出恢复，Jetson 和外设能独立供电。换板后恢复只能说明故障位于这一级，不能反过来推定是哪个元件开路。

六、记录

  1. 本地输入输出全断时，改 /etc/shadow 里的哈希是拿到 shell 最快的办法，前提是能物理接触存储卡；改成哈希之前要先想清楚，这等于给所有能碰到卡的人开了后门。
  2. 多网卡连不上，先查子网是否重叠。子网重叠导致的不是“连不上 AP”，而是关联成功后拿不到可用地址、或者能拿到但回程走错接口，所以用 ip route get 看出口比看关联状态更有用。
  3. lsusb -t 只反映枚举结果。设备不在树里，说明枚举失败，原因可能是供电、链路或芯片，不能直接下“芯片烧了”的结论。
  4. 电源问题按节点量电压，把范围缩到某一级，再用换件验证。从“没输出”直接跳到某个元件开路，中间隔了好几种可能性。
